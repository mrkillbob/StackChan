# Implemented remote/provisioning milestone

Code, not deployed: provisioning.py reuses HomeLab's one-use DeviceRegistry redemption to produce a bounded volatile SCPG v1 frame; the C++ provisioning_frame.hpp parses the same frame and enforces a60s,one-use,device-bound window. No trust/qualification boolean is accepted from frame bytes. Owner authorization and route qualification must come from trusted code; defaults deny. No USB reader, physical Pair control or NVS credential storage is connected in the currently flashed image. The broker does not independently prove a provider's identity.

remote_gateway.py supplies a lazy WebSocket sidecar with admission, one active device connection, bounded streaming and provider teardown. It starts no listener on import. Production needs verified TLS or a verified loopback proxy; plaintext fixtures bind localhost only and send fixture=true, which real firmware rejects. With no provider factory, authenticated upgrades return503. Separate API personas or Codex thread references are not supplied as Mira.

durable_audio_registry.py uses the existing SQLite store as authoritative state on each check, so owner revocation in another process is observed without a stale in-memory credential cache. It has no credential-issuance/revocation interface. Existing HomeLab owner APIs remain responsible for authority.

Inspected HomeLab revision f8f47b8e26cee976ff208722f7c6e667fe19a4aa: DeviceRegistry supports one-use5min codes, hashed credential persistence and atomic revocation. /api/devices/pairing and /revoke require owner sessions; /redeem consumes a code. Its HTTP server is ThreadingHTTPServer, not a WebSocket implementation. attach_external_session stores a reference only; it does not attach to a provider call. No HomeLab source was changed; its four pre-existing untracked plan files remain untouched.

Existing deployment evidence: a historical Mac-hosted tailnet HTTPS Serve route to loopback18765 and phone pairing are documented. This is not proof of current service availability. Mac hosting does not satisfy Mac-off production. ESP32 has no implemented Tailscale client, and tailnet-only hostname reachability from ordinary Wi-Fi is not established. Saved Codex project metadata lists a Raspberry Pi connection, but no remote execution tool/current Pi HomeLab runtime or matching SSH alias was available to verify a deployment target. Do not assume a live Pi gateway or publish a new public endpoint.

A future deployment can reuse existing HomeLab state/owner API on a verified always-on host and add this WebSocket sidecar behind its existing trusted TLS route. Runtime requires Python3.14.7 and the separately installed websockets17.2 package (currently project-local, not a HomeLab dependency). Actual provider/codec adapters, host readiness, TLS/DNS/router reachability and entitlement remain unverified.

The exact Mira attachment boundary is absent: no supported public interface inspected exposes audio attachment to this existing dot room. Provider factory deliberately remainsNone. The code's session reference and identity_verified flag are integration contracts requiring independent adapter evidence; they are not that evidence. Native dot calls preserve identity; API-created Live sessions and Codex thread resumes do not establish this room binding. See PLATFORM-BINDING-RESEARCH.md.

Validation includes39 Python tests, a bounded localhost WebSocket protocol/consent/revocation fixture, temporary SQLite restart/cross-process revocation, and a cross-language C++ decode/window test. Synthetic grants are confined to test memory/temporary state and cannot authorize the robot. No live access, provider call, camera/motion, audio IO, deployment, firmware rebuild or flash occurred.
