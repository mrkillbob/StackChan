# Stock software retention and proposed integration

Status: source inventory and proposed design, not an implemented stock-shell integration. Current committed implementation is the reviewed companion receiver at69f885e. Do not flip STACKCHAN_COMPANION_BOOT off to restore menus: that invokes normal vendor startup, servo initialization, settings writes and possibly cloud/wake-word audio.

Compared with official source1b5765599fba8aaad1811d9a79358ccc7051f5f3, no stock app directory or menu was deleted. main.cpp adds an early nonreturning companion boot path; the stock path is unreachable with the current default. HAL adds initCompanion instead of normal init; board startup skips power saving/auto shutdown and camera under companion builds. CMake substitutes read-only settings/board helpers for vendor dependency implementations. All eight stock apps remain source-side: Launcher, AI.Agent, Avatar, ESP-NOW control, App Center, EzData, Dance, Setup. Their existing user functions are currently unavailable in the flashed companion UI, not retained as working UI. Board/display/touch/audio codecs and read-only saved Wi-Fi/UUID are reused. NVS error now halts rather than erases. Camera, servos/idle motion, BLE remote control, ESP-NOW transmit, vendor cloud, OTA, microphone capture and speaker playback do not start automatically. Audio requires physical Allow plus host admission.

Recommended integration: reuse the stock Mooncake launcher, icons, layout and home navigation. Add a Mira Companion app with Open/Tick/Close lifecycle around the existing receiver/session; Close revokes pairing/connection/audio before returning to Launcher. Keep the existing eight menu identities. Local display/avatar rendering, brightness/volume and status can be restored with safe initialization; cloud/app downloads, account/Wi-Fi provisioning, remote avatar/video, AI.Agent, dance/motion and calibration remain visibly gated until their exact effects are qualified and individually selected. Do not call normal Hal::init or original Avatar::onOpen unchecked: init powers servos; Avatar opens a vendor WebSocket service. Persistent settings must be audited, since current read-only setters would otherwise make controls appear to save when they do not. The launcher currently auto-starts StartupWorker if configuration is absent: safe shell must suppress account/cloud onboarding. Stock launcher GetStackChan.update also needs a safe no-motion object/lifecycle; do not assume absent motion initialization is harmless.

Tests before keeping this integration: safe-init spy proves no servo/camera/network/credential/OTA start; stock-menu registration and open/return lifecycle; Companion Close/Mute clears frame, grant, socket and codec state; grant after Mute with Wi-Fi connected still needs Connect; physical Allow + host authorization gate audio; repeated app open/close has no stale callback/task or USB ownership; full ESP-IDF build; separately approved hardware acceptance later.

Initial tools recommendation: bounded IR receive/capture and NEC decode, plus I2C device discovery/status (no arbitrary register writes). These use present hardware, not hypothetical modules. M5 official docs map IR_SEND GPIO5, IR_REC GPIO10, internal I2C SCL11/SDA12, ST25R3916 address0x50. SDK driver API exists; current firmware has no IR or ST25R3916 implementation. The existing internal I2C bus is shared with PMIC/audio/touch, so diagnostics must use its handle and serialize access, avoid probing busy audio, reject reserved addresses and bound timeout/results. Grove A is GPIO2/1, B9/8, C17/18, with5V supply; supply voltage is not evidence of5V-tolerant GPIO. No wiring or external module purchase is authorized. IR transmission can be added only with explicit per-action confirmation, bounded carrier/timing and no automatic repeat.

Games: Snake is the smallest recommended first game, Pong second, block puzzle third, all feasible as local320x240 UI/game-state work. A USB HID input adapter is a separate qualification item; touch controls can exercise state logic without claiming a plugged-in controller worked. ESP32-S3 is BLE, not Bluetooth Classic. Official CoreS3 schematic includes USB_OTG_EN and boost/VUSB power control, and M5 documents both USB-C ports as data-capable. That does not prove the robot base port will safely source controller power in host mode. Internal USB PHY ownership conflicts with current USB Serial/JTAG provisioning; host mode must be mutually exclusive and return safely, never repurpose provisioning silently. Exact board path/VBUS budget/cable and controller HID descriptors are unqualified. Do not claim all Xbox/PS controllers, hubs or proprietary protocols work. Games should pause/close companion audio, have bounded tick/input queues, handle controller disconnect, and remain silent by default.
